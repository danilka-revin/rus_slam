## 1. Назначение окна

Окно **«Сервис»** (`view-console`) — единая точка обслуживания робота
оператором смены. Оно закрывает четыре задачи, продиктованные регламентом
конкурсного задания № 2 и эксплуатацией изделия:

| № | Задача | Регламент (задание № 2) |
| :-: | :--- | :--- |
| 1 | **Доступ к грузу**: ввод пароля, открытие/закрытие ячейки хранения (грузового отсека), журнал доступа | «груз … защищен от несанкционированного доступа», «защита груза от посторонних лиц» (критерии 6, 9) |
| 2 | **Статистика**: рейсы, пробег, энергия, груз, события (знаки, светофор, объезды), выгрузка отчёта | «отчётность», «сбор, хранение и управление диагностическими данными», «информирование о статусе задания» (критерий 13) |
| 3 | **Двигатели**: под каждый из 8 двигателей (4 рулевых NEMA 23 + 4 тяговых BLDC) — поле ввода и кнопка «Ввод» для ручной подачи команды, квитирование, лог кадра UART | «безопасное движение», «готовность к развитию», «программно-аппаратный комплекс» (критерии 7, 8) |
| 4 | **Состояние аккумулятора**: пак 12S3P LiFePO4 — напряжение, SOC, ток, мощность, остаток ёмкости, запас хода, пороги защиты, телеметрия по модулям | «встроенный источник питания», «безопасность» (критерии 7, 8) |

Окно не заменяет существующие вкладки «Пульт», «Ходовая», «Миссия»,
«Сенсоры», «Безопасность», «Журнал» — оно дополняет их
эксплуатационным (сервисным) контуром.

## 2. Требования к решению

### 2.1. Функциональные требования (ФТ)

**ФТ-1. Ячейка хранения (замок):**
* ФТ-1.1 поле ввода пароля (маскированный ввод, цифровая клавиатура, `Enter`);
* ФТ-1.2 проверка пароля, открытие/закрытие замка, индикация состояния
  «ЗАКРЫТО / ОТКРЫТО / БЛОКИРОВКА»;
* ФТ-1.3 смена пароля (текущий + новый + повтор);
* ФТ-1.4 блокировка ввода после 5 неудачных попыток на 30 с с обратным отсчётом;
* ФТ-1.5 журнал доступа (кто/когда/результат), устойчивый к подделке
  (хеш-цепочка записей);
* ФТ-1.6 альтернативные каналы: «QR» и «RFID» (имитация считывания);
* ФТ-1.7 предупреждение при открытии вне площадки загрузки/выгрузки, если
  в отсеке есть груз;
* ФТ-1.8 пароль не хранится в открытом виде (SHA-256 + соль), значения по
  умолчанию документированы для судей (заводской PIN `2580`).

**ФТ-2. Статистика:**
* ФТ-2.1 живые показатели сессии: пробег, энергия (Вт·ч), расход (Вт·ч/км),
  средняя/максимальная скорость, время в движении, груз;
* ФТ-2.2 накопительные показатели: рейсы, пробег, энергия, перевезённый груз,
  события (знаки по типам, светофор, объезды, ручные вмешательства);
* ФТ-2.3 таблица последних рейсов (время, маршрут, дистанция, груз, энергия,
  результат);
* ФТ-2.4 графики: энергия по рейсам и история SOC/скорости за сессию;
* ФТ-2.5 экспорт: CSV (для таблиц), JSON (машинный отчёт), печатный отчёт
  (HTML → печать/PDF браузера);
* ФТ-2.6 персистентность в `localStorage` с версионированием схемы;
* ФТ-2.7 сброс статистики с подтверждением.

**ФТ-3. Двигатели:**
* ФТ-3.1 4 карточки модулей (FL/FR/RL/RR), в каждой два канала:
  рулевой (NEMA 23, угол в градусах) и тяговый (BLDC Xiaomi M365 Pro, ШИМ/мощность);
* ФТ-3.2 в каждом канале: числовое поле ввода + кнопка **«Ввод»**, а также
  быстрые кнопки-«джоги» (шаг ±5°, ±45°, тяга −20 % / 0 / +20 %);
* ФТ-3.3 квитирование: целевое значение → кадр UART (10 байт, CRC16/Modbus) →
  HEX в журнале → применение к модели;
* ФТ-3.4 отображение факта: угол, ошибка, шаги, «хоминг», статус, для тяги —
  об/мин, м/с, ток, температура, напряжение модуля;
* ФТ-3.5 сервисный режим «стенд»: авто/миссия/телеуправление блокируются,
  робот стоит, вращаются только модули; выход из режима — явной кнопкой;
* ФТ-3.6 интерлоки: ввод запрещён при `E-STOP` и при активном авторежиме
  (предлагается сначала остановить миссию);
* ФТ-3.7 групповые операции: «Стоп все», «Момент вкл/выкл», «Хоминг всех»,
  «Синхронный угол» (задать одинаковый угол всем модулям).

**ФТ-4. Аккумулятор:**
* ФТ-4.1 модель 12S3P LiFePO4 (36 банок 32700): 30.0–43.8 В, 18.6 А·ч, 714.2 Вт·ч;
* ФТ-4.2 расчёт SOC по OCV-кривой LiFePO4 с учётом просадки под током;
* ФТ-4.3 индикация: напряжение, ток, мощность, остаток Вт·ч, запас хода,
  температура, состояние (разряд/заряд/покой);
* ФТ-4.4 пороги из `config/safety.yaml`: 35.5 В — ползучий режим,
  33.5 В — аварийный стоп; отображение текущего уровня риска;
* ФТ-4.5 балансировка: min/max/Δ по 12 группам ячеек (модель);
* ФТ-4.6 телеметрия по 4 модулям: напряжение, ток, температура, вклад в расход;
* ФТ-4.7 история SOC за сессию (график) и счётчик циклов заряда;
* ФТ-4.8 быстрые действия: «На базу · зарядиться» (существующий сценарий),
  задание целевого процента.

### 2.2. Нефункциональные требования (НФТ)

| Код | Требование |
| :--- | :--- |
| НФТ-1 | Никаких внешних зависимостей и сборщиков: чистые `HTML/CSS/JS`, работа по `file://` |
| НФТ-2 | Совместимость с существующим пультом: тема ZMK Vision (тёмный сайдбар `#101b17`, акцент `#d5ff45`), светлая/тёмная темы |
| НФТ-3 | Единый главный цикл `requestAnimationFrame`; тяжёлые перерисовки — не чаще 4 Гц и только для видимой вкладки |

| НФТ-5 | Отказ `localStorage` (приватный режим) не должен ломать пульт: деградация до памяти сессии |
| НФТ-6 | Русскоязычный интерфейс, единицы СИ, формат времени `чч:мм:сс` |
| НФТ-7 | Адаптивность: 2 колонки → 1 колонка при ширине < 1100 px |

## 3. Пользовательские сценарии

**С-1. Выдача груза получателю (основной).** Робот прибыл на площадку Б →
оператор открывает окно «Сервис» → вводит PIN (или QR/RFID) → замок
открывается → оператор забирает груз → нажимает «Груз сдан» (существующая
кнопка подтверждения) → статистика фиксирует рейс → замок закрывается
автоматически через 30 с или кнопкой «Закрыть».

**С-2. Загрузка на площадке А.** Оператор вводит PIN, открывает отсек,
укладывает груз, закрывает замок. Система фиксирует массу (ползунок «груз»)
и запрещает старт миссии с открытым замком.

**С-3. Стендовая отладка модуля.** Инженер останавливает миссию, включает
«Сервисный режим · стенд», в карточке модуля FL задаёт угол `45` и нажимает
«Ввод» — рулевой модуль поворачивается, в журнале появляется HEX кадра
`AA 55 01 11 94 ...`, в карточке виден факт угла и ошибка. Аналогично
подаётся тяга `+20 %` и контролируются об/мин, ток, температура.

**С-4. Диагностика АКБ.** Оператор видит напряжение 35.2 В, уровень
«ПОЛЗУЧИЙ», остаток 8 %, запас хода 6 км → нажимает «На базу · зарядиться»,
задаёт цель 100 %.

**С-5. Отчётность.** По итогам смены оператор нажимает «Отчёт (печать)» —
формируется печатная форма: сводка, рейсы, события, состояние АКБ; либо
выгружает CSV/JSON для дальнейшей обработки.

## 4. Термины и обозначения

| Термин | Значение |
| :--- | :--- |
| **Модуль (pod)** | Поворотно-тяговый узел: NEMA 23 (руль) + мотор-колесо Xiaomi M365 Pro (тяга) |
| **Канал** | Один двигатель модуля: `steer` или `traction` |
| **ШИМ / PWM** | Задание тяги в протоколе: −1000…+1000 (знак — направление) |
| **SOC** | State of Charge, оценка заряженности АКБ, % |
| **OCV** | Напряжение холостого хода (по нему строится кривая SOC) |
| **Стенд** | Сервисный режим: робот обездвижен, модули управляются вручную |
| **Рейс** | Интервал автономного движения от старта миссии до прибытия/сдачи груза |
| **Аудит-цепочка** | Журнал доступа, где каждая запись содержит хеш предыдущей |

## 5. Архитектура

### 5.1. Слои и файлы

```text
gui/
├── index.html        (+ вкладка «Сервис», панели 4 блоков, модальные окна)
├── styles.css        (+ стили сервисного пульта)
├── console-core.js   (НОВЫЙ) чистый слой логики без DOM:
│                       RSPack   — модель АКБ 12S3P LiFePO4
│                       RSUart   — кадры протокола (CRC16/Modbus), HEX
│                       RSVault  — PIN-хранилище, блокировки, аудит-цепочка
│                       RSStats  — накопительная статистика, рейсы, экспорт
│                       RSFmt    — форматирование чисел/времени
├── console.js        (НОВЫЙ) DOM-слой окна «Сервис»: карточки модулей,
│                       клавиатура PIN, графики, таблицы, экспорт
├── app.js            (доработка) интеграция: модель АКБ, события,
│                       метрики сессии, сервисный режим, светофор
└── vision.js         (доработка) светофор в WORLD
```

Порядок загрузки скриптов (важно: `console-core.js` определяет `window.RS`
раньше, чем `app.js` начинает им пользоваться):

```html
<script src="console-core.js"></script>
<script src="vision.js"></script>
<script src="app.js"></script>
<script src="console.js"></script>
```

### 5.2. Поток данных

```text
                 ┌──────────────────────────────────────────┐
 состояние симуляции (state)  ──►│              console-core.js             │
                 │  RSPack (SOC/V/I/энергия/запас хода)     │
   app.js ───────┤  RSStats (метрики, рейсы, события)       │
   (тик 60 Гц)   │  RSVault (PIN, блокировки, аудит)        │
                 │  RSUart (кадр 10 Б + CRC16)              │
                 └───────────────┬──────────────────────────┘
                                 │ render (4 Гц, только видимая вкладка)
                                 ▼
                          console.js (DOM)
                      панели: Замок / Двигатели / АКБ / Статистика
                                 │ действия оператора
                                 ▼
              state (сервисный режим, команды модулей, зарядка)
```

### 5.3. Принципы

1. **Разделение логики и представления.** `console-core.js` не знает о DOM,
   поэтому тестируется в Node без браузера.
2. **Обратная совместимость.** Все существующие элементы и сценарии
   (`app.js`, `vision.js`) сохраняются; новые функции подключаются
   опционально через `window.RS` с проверкой наличия.
3. **Безопасные интерлоки.** Любое ручное вмешательство возможно только
   вне авторежима и вне E-STOP; сервисный режим явно индицируется.
4. **Данные не теряются.** Статистика и аудит сбрасываются на диск
   (`localStorage`) периодически и по событию.

## 7. Алгоритмы

### 7.1. Модель АКБ 12S3P LiFePO4

Параметры (совпадают с `docs/TECHNICAL_SPECIFICATION.md`):

```text
12S3P, банки 32700 (3.2 В / 6200 мА·ч), номинал 38.4 В,
диапазон 30.0…43.8 В, ёмкость 18.6 А·ч = 714.2 Вт·ч,
внутреннее сопротивление сборки ≈ 0.075 Ом, BMS 60 А, предохранитель 25 А
```

**Кривая OCV** (на элемент, кусочно-линейная):

| U эл., В | 2.50 | 2.80 | 3.00 | 3.10 | 3.20 | 3.25 | 3.30 | 3.33 | 3.35 | 3.40 | 3.45 | 3.65 |
| :--- | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| SOC, % | 0 | 3 | 7 | 10 | 15 | 30 | 50 | 70 | 85 | 95 | 98 | 100 |

* `socFromVoltage(U_пак)` — обратная интерполяция по кривой;
* `voltageFromSoc(soc)` — прямая интерполяция;
* терминальное напряжение под нагрузкой: `U = OCV − I·R`, при заряде
  `U = OCV + |I|·R`;
* разряд считается **по энергии**: `dE = U·I·dt/3600`, `dSOC = dE/714.2·100 %`;
* запас хода: `range = E_остаток / расход` где расход берётся из сессии
  (Вт·ч/км), при отсутствии данных — паспортные 20–25 км на полный заряд;
* пороги: 35.5 В — «ползучий» (SOC-индикация «низкий заряд»),
  33.5 В — «критический» (гейт безопасности закрывается).

### 7.2. Ручная команда двигателю

```text
1. Оператор вводит значение (угол, °) или ШИМ (%, −100…+100)
2. Валидация: диапазон угла ±180°, ШИМ ±100 % (в протоколе ±1000),
   шаг дискретности 0.03° (33.33 шага/град), проверка интерлоков
3. Формирование кадра: AA 55 | ID | STEER_CDEG(i16 BE) | PWM(i16 BE) |
   FLAGS(bit0 ENABLE, bit1 HOME) | CRC16(BE)
4. HEX выводится в журнал; кадр применяется к модели модуля
5. Обновление целевых значений: steer → target, pwm → тяга
6. Модель отрабатывает ограничения: скорость перекладки 360°/с,
   разгон тяги 2.6 (м/с)/с, ток по ШИМ, температура по нагрузке
7. Квитирование: если |ошибка| ≤ 0.5° — «в позиции»
```

Шаг 6 исполняется в симуляторе при сервисном режиме: угловой сервопривод
сходится к цели с ограничением скорости, колесо разгоняется/тормозится,
накапливается путь колеса (для контроля энкодера).

### 7.3. Замок ячейки (PIN)

```text
Хранение:  salt = random 16 байт (hex)
           pinHash = SHA-256(salt + ":" + pin)
Проверка:  attempts < 5 ? compare(hash(input)) : lockout 30 c
Успех:     fails = 0, lockUntil = 0, запись аудита {action:"unlock", ok:true}
Неудача:   fails++, запись аудита {action:"unlock", ok:false, fails}
Аудит:     каждая запись хранит prevHash; hash = SHA-256(prevHash + поля)
           → обнаружение правки/удаления записи (tamper-evident)
Смена PIN: требуется текущий PIN, новый 4–8 цифр, повтор;
           смена фиксируется в аудите и статистике
```

Автозакрытие: через 30 с после открытия, если груз снят/уложен
(настраиваемый таймер), либо вручную.

### 7.4. Рейс и события

* **Рейс** начинается при переходе `state.auto: false → true` и завершается
  при `true → false` либо по прибытии на финальную точку/после сдачи груза;
  записываются дистанция, энергия, время, груз, средняя и максимальная
  скорость, результат.
* **События** инкрементируются в точках симуляции:
  знак (`stop`/`pedestrian_crossing`/`speed_bump`) — при срабатывании зоны,
  светофор — при остановке на красный и возобновлении на зелёный,
  препятствие — при срабатывании объезда/тупика, ручное вмешательство — при
  «Ввод» в карточке двигателя.

## 10. Безопасность и отказоустойчивость

| Риск | Мера |
| :--- | :--- |

| Выход за пределы механики | валидация диапазонов (угол ±180°, ШИМ ±1000), предупреждения |
| Падение `localStorage` | `try/catch`, деградация до памяти процесса |
| Потеря статистики | запись раз в 15 с, при завершении рейса и `beforeunload` |
| Перерисовка тяжёлых графиков | частота 4 Гц, только для видимой вкладки |

## 13. Ограничения и развитие

**Ограничения текущей ревизии:**
* GUI остаётся автономным симулятором; связь с ROS 2 — через
  `rosbridge_server` (см. `GUI.md` §9);
* электрический замок отсека — модель (в железе требуется реле/соленоид,
  управляемый GPIO бортового ПК, см. `pcb/CONNECTOR_PINOUTS.csv`);
* PIN/QR/RFID — программная имитация; в железе: RC522 (SPI) и камера QR.

**Дорожная карта:**
1. Мост `rosbridge`: топики `/cargo/lock` (`std_msgs/Bool`), `/battery`
   (`rus_slam_interfaces/BatteryInfo`), `/modules/state` — вместо модели;
2. реальный QR-сканер (камера) и RFID RC522 с белым списком меток;
3. экспорт отчётов в PDF на стороне бортового ПК (текущий — печать браузера);
4. журнал статистики в SQLite/бортовом хранилище с синхронизацией на сервер
   диспетчера;
5. роли операторов (сменный инженер/получатель) с разными правами.
